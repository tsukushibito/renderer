# 3D 見下ろし型ローグライトサバイバーの制作計画

プレイヤーは群れの隙間を読んで移動し、自動攻撃で敵を倒す。経験値を拾いに戻る危険と、次の強化で得られる利益を天秤に掛ける。敗北後には別の強化の組み合わせで再挑戦できる。この一連の判断が面白いことと、制作者が敵・強化・ステージを継続して追加できることを、Sashiko の最初のゲームで確かめる。

## 制作ロードマップ

| 節目 | プレイヤー・制作者が手にするもの | 次へ進む判断材料 |
|---|---|---|
| 1. 操作できるアリーナ | 実寸の仮素材を配置した見下ろし画面で、移動、追従カメラ、障害物や敵との接触を体験する。 | 人が退路を見分けて操作できる。同じ配置と入力をヘッドレスで再生すると、位置と接触結果が一致する。制作者が配置データを編集すると両方に反映される。 |
| 2. 遊びが一周する | 敵を倒して経験値を回収し、効果の異なる強化を選び、敗北して再挑戦する。開発時は同じゲームを代表的な終盤配置から開始できる。 | 初見の人が回収のリスクと強化の違いを理解して選べるかを観察する。序盤と混戦時の操作感・画面の読みやすさ・フレーム時間を比較し、次に直す箇所を決める。 |
| 3. ランごとの違いと制作性 | 動きの異なる敵、役割の異なる攻撃、強化同士の相互作用、ステージ変化、ランをまたぐアンロックを加える。HUD、音、予兆で判断に必要な情報を伝える。 | 別のビルドで通しプレイし、勝ち筋が変わる。再起動でアンロックが残り、一時効果は新しいランで初期化される。別の制作者が既存型の敵・強化・配置を追加し、変更からプレイ確認までの手順と時間を記録できる。 |
| 4. 完成用アートと品質の確定 | 実際のプレイカメラで基準となる一区画と一体を仕上げ、背景・キャラクター・演出を順に独自アートへ置き換える。対象機材、画質、最大負荷、対応入力を確定する。 | 差し替え前後で同じ戦闘を再生し、接触・報酬・タイミングを照合する。完成品質の終盤で予兆を読み、目標機材でフレーム予算を満たせる。 |
| 5. 配布とエンジン評価 | 新しい環境に配布物を入れ、起動、設定、プレイ、セーブ、再起動まで通す。 | 開発用の原本・キャッシュがない環境で第三者が遊べる。リリース後を想定したコンテンツ追加を一度通し、Sashiko が支えた機能、ゲーム固有の実装、残る制作上の障害を記録する。 |

作品の舞台、ランの長さ、敵や強化の種類・数はプレイテストで決める。基準 PC には既存の実機検証環境を使える Windows を第一候補とする。最初の一区画・一体は制作手順を通すための単位で、完成版の規模は終盤の遊びと計測結果から定める。[既存の実機環境と訓練場の検証](../verification/current.md#engine-integration)

## 直近の作業順

作業の状態・担当・依存関係は Beads の親課題 `renderer-zgrl` に集約する。最初に並行して取り組めるのは次の三件。ID はすべて同じ親の子課題を表す。

| Beads | 最初の成果物 | 完了時に答えられる問い |
|---|---|---|
| `renderer-zgrl.2` | 序盤・終盤の代表場面と計測条件。カメラ距離、敵・攻撃・ドロップ数、対象 PC、解像度、仮のフレーム予算、プレイテストの観察項目を決める。 | 同じ条件を別の人が再現し、画面から次の退路や被弾の理由を読み取れたかを比較できるか。 |
| `renderer-zgrl.3` | 無料公開の PBR 環境素材と、骨格・移動クリップを持つキャラクターの取込。別モデルへの差し替えを一度通す。 | 出典、利用・再配布条件、版、取得・変換手順を追えるか。モデルを替えてもゲーム側の移動・当たり判定・報酬を維持できるか。 |
| `renderer-zgrl.4` | 訓練場から独立したゲーム入口と、GPU なしで動く固定周期の更新。編集可能な初期配置、乱数 seed、更新ステップごとの入力を受け取る。 | 配置を変えて再実行できるか。同じ初期条件と入力列なら、描画頻度によらず同じ位置に到達するか。 |

三件を合わせて `renderer-zgrl.5` で見下ろしアリーナを実際に操作し、ウィンドウとヘッドレスの状態を照合する。続く `renderer-zgrl.6` で撃破から強化・敗北・再挑戦までをつなぐ。`renderer-zgrl.7` では開発用の開始状態を渡して終盤へ直行し、同じ生成・更新・描画処理で最初の混戦計測を行う。通しプレイも残し、道中で強化を選ぶ体験と長時間プレイでの資源推移を観察する。

## ゲームとエンジンの境界

ゲーム側が敵の行動、ダメージ、当たり判定、経験値、強化、ランの乱数と状態を所有する。描画には更新後の姿勢・材質・演出を渡す。公開 Renderer、PBR、照明ベイク、アセット ID・cook・配布、訓練場の入力再生と画像照合の知見を利用する。訓練場と Bistro は描画・資産の回帰を再現する場として維持する。新しい共通機能の候補は、実際の敵やステージを追加して分かった重複や制作上の障害から選ぶ。[既存のエンジン統合](../guides/tooling.md#scene-materials)・[アセットパイプライン](asset-pipeline.md)

アートとゲームルールは別々に編集できるようにする。敵の定義は安定した ID で見た目を参照し、素材側で単位・前方軸・足元・骨格とクリップの対応を整える。現行の装備 cook は静的 glTF が対象で、スキン・モーフを受け付けない。最初のキャラクターで必要なスキン・クリップの取込と再生を通し、既存のポーズ描画まで接続する。写実性はプレイ時の距離での材質・光・接地感・動きで判断し、攻撃予兆と経験値が混戦に埋もれないかも同じ画面で確認する。[装備 cook の対応形式](../guides/tooling.md#equipment-cook)

終盤の計測では機材・ビルド・画質・seed・開始状態を固定し、CPU と GPU の時間、フレーム間隔の p95・p99、個体数、メモリ使用量を記録する。初回は仮素材・実装済みの敵や演出で基準値を取り、種類とアートが揃った段階で再測定する。Renderer を変更した場合は、既存の実機・画像回帰と準備容量内の定常フレームのメモリ検証を適用する。実測値と未確認範囲は検証文書へ反映する。[定常フレームのメモリ方針](implementation-policy.md#steady-state-memory)・[検証記録](../verification/current.md)
