# ライブインスペクタの設計

プレイ中に開かなかった扉を画面で選ぶ。開発者はその個体を LLM に渡し、「どの鍵を要求し、実際にどの鍵が渡されたか」を調べられる。扉が既に消えていても、記録があれば解錠を拒否した時点の事実に戻れる。この操作を、画面のあるゲーム、実機、ヘッドレス実行で共通にする。

**初版はゲーム自身が常駐し、一つの標準入出力接続で NDJSON 要求を受ける。** 起動時に接続相手が確定するため、セッション探索や要求ごとのプロセス生成を省ける。固定更新境界の読み取り、スナップショット、イベントの待機・購読、停止・1 tick 送りを、独立したヘッドレスゲームで利用できる。観測 API は ECS と配列の両方から実装できる。[実行とプロトコル v1](../guides/development.md#live-inspector)・[初版の検証](../verification/current.md#live-inspector)

Rust ホストは `Session::watch` で購読し、`Session::cancel` で終了を要求する。`Session::poll` がその購読の終了通知を返すと、同じ ID と購読枠を再利用できる。NDJSON の `cancel` も同じ終了処理を通る。解除後もワールド・tick・ジャーナルの保持期間は引き継がれる。

Survivor の開発構成では、表示済みフレームを右クリックするとプレイヤーまたは敵の ID が標準エラーに出る。
NDJSON の `selected` から同じ選択を読み取れる。別プロセスからの後付け接続、実行値の編集・保存は後続の設計である。

## 先行エンジンから採る判断

| 方式 | 利点と制約 | 採用する判断 |
|---|---|---|
| Godot は Remote ツリーでノードを選び、エディタが選択中の ID を指定して値を再取得する。ツリーと値の更新間隔は独立している。 | 実行中の対象を見つけやすい。周期的な取得の間に状態が戻ると、最新値からその変化を復元できない。 | 選択対象を絞った値の取得と、ゲーム側でのイベント記録を組み合わせる。[デバッグ操作](https://github.com/godotengine/godot-docs/blob/master/tutorials/scripting/debug/overview_of_debugging_tools.rst)・[エディタの更新処理](https://github.com/godotengine/godot/blob/master/editor/debugger/editor_debugger_node.cpp) |
| Unity の標準 Inspector はシリアライズ対象を表示し、フィールド編集時に C# のプロパティ setter を経由しない。Entities には Authoring・Runtime・Mixed の表示がある。 | 型から UI を作れる。保存先と実行値を判別する必要があり、setter にある整合性処理を直接編集が迂回し得る。 | 読み取りの登録を自動化する。書き込みは型の所有者を経由し、画面には値の出典を表示する。[シリアライズと Inspector](https://docs.unity3d.com/cn/2022.2/Manual/script-Serialization.html)・[Entities のデータモード](https://docs.unity.cn/Packages/com.unity.entities@1.0/manual/editor-authoring-runtime.html) |
| Unreal Engine は Play／Simulate 用にレベルを複製し、対象の変更を制作元に戻せる。アニメーション用 Rewind Debugger は記録区間の個体と状態を時系列で表示する。 | 調整と保存を別々に選べ、消滅した対象も追える。永続化には制作元との対応が要り、調査できる過去は記録範囲に依存する。 | 実行編集と制作元への保存を独立させ、履歴には対象・期間・欠落を明記する。[Play と Simulate](https://dev.epicgames.com/documentation/unreal-engine/ineditor-testing-play-and-simulate-in-unreal-engine)・[Rewind Debugger](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-rewind-debugger-in-unreal-engine) |
| Bevy Remote Protocol は個体とコンポーネントを検索・取得・購読できる。通信は別プラグインで、取得にはリフレクション可能な型が使われる。 | 複数クライアントが同じ操作を使える。値の列挙だけではゲーム固有の判断理由は伝わらない。 | 通信とストレージを交換可能にし、ゲームが型付きの結果・理由・当事者を登録できるようにする。[プロトコル](https://docs.rs/bevy/latest/bevy/remote/index.html)・[変更購読の実装](https://docs.rs/bevy_remote/latest/src/bevy_remote/builtin_methods.rs.html) |

## 個体・項目・時刻

| 概念 | 契約 |
|---|---|
| セッションとワールド | 一回の起動にセッション ID、独立に進むシミュレーションにワールド ID を発行する。サーバーとクライアントは別ワールドとして表示する。再起動時は古いハンドルを失効させる。 |
| 観測する個体 | 外部 ID は不透明な文字列とし、セッション・ワールドの中で破棄済み個体と再利用先を区別する。内部では世代付きスロット等を使える。画面の選択結果に表示時の個体 ID を保持し、クリック後に対象が消えていたら消滅を返す。配置 ID、原型 ID、表示名は別の属性とする。 |
| 型と項目 | スキーマは安定した型・項目 ID、版、表示名、説明、型、単位、参照先、読み書きの可否を持つ。イベントも引数と役割を宣言する。名前変更で表示名だけが変わる。意味・型の非互換変更は版で判別し、互換性のない保存済みの監視設定を明示する。 |
| 観測時点 | 固定更新が完了した `tick` と、ワールドの確定状態を識別する `revision` を返す。一時停止中に編集を確定した場合は同じ tick のまま版が進む。表示補間後の位置や非同期の計測値には別の時計と採取時刻を付ける。 |
| スナップショット | 指定した対象・項目を一つの確定時点からコピーした不変データ。サーバーが ID、収録範囲、有効期限を返す。期限内は別の CLI プロセスから同じ値を読める。未収録の項目は `NOT_CAPTURED`、期限後は `SNAPSHOT_EXPIRED` を返す。 |
| 出典 | 項目ごとに対応がある範囲で原型値・配置の上書き・実行値を示す。現在 HP のような派生・実行専用の項目にはその種別を付ける。生成された扉とその表示用メッシュなど、一個体から複数の所有元への参照も表せる。 |

### ゲームとの接続

ゲーム側が実装する境界は、対象の検索、項目の記述、確定時点での値の読み取り、イベントの発行、許可した編集の適用である。読み取りは副作用を持たず、選択中の値だけを呼び出し側のバッファへ書く。標準の数値・列挙・参照・配列は登録情報から UI を生成する。長い配列は範囲指定で読み、カスタム表示にも CLI で取得できる構造化表現を用意する。

ECS なら個体ハンドルと登録コンポーネントから記述・読み取りを生成できる。オブジェクト指向なら所有者がプロパティを記述し、配列主体なら各サブシステムがハンドルから行を解決する。いずれもポインタや配列添字をクライアントに公開する必要はない。物理と AI が同じ敵の異なるデータを持つ場合は、一つの観測個体の下に両方の項目を出し、詳しい調査では所有元へ辿れるようにする。

## 後付け接続用 CLI の設計例

以下は将来のローカル IPC クライアントの操作案である。初版で実行する場合は[常駐 NDJSON の例](../guides/development.md#live-inspector)を使う。後付け接続では最初にセッションとワールドを選ぶ。GUI で選んだ場合はセッション・ワールド・個体 ID をまとめてコピーできる。

```sh
sashiko inspect sessions
sashiko inspect find --session play-1 --world game --tag door --limit 5
sashiko inspect schema --session play-1 --world game --type Door
sashiko inspect read --session play-1 --world game --object d-17 --fields state,required_key
```

`find` は ID・型・名前と次ページのカーソルを返す。一覧の版が失効した場合は再検索を要求する。`schema` で扉のイベントと当事者の役割を調べたら、次の解錠拒否を待つ。この要求は登録後のイベントを対象とし、CLI の呼び出し元でタイマーポーリングする必要がない。

```sh
sashiko inspect wait --session play-1 --world game --object d-17 --event unlock_denied --capture self.state,actor.held_key --timeout-ms 30000
```

```json
{
  "ok": true,
  "session": "play-1",
  "world": "game",
  "event": {
    "sequence": "817",
    "tick": "1842",
    "type": "unlock_denied",
    "self": "d-17",
    "actor": "p-2",
    "required_key": "basement",
    "presented_key": "garden"
  },
  "snapshot": {
    "id": "snap-91",
    "tick": "1842",
    "revision": "1901",
    "phase": "end_of_tick",
    "fields": {"d-17": ["state"], "p-2": ["held_key"]},
    "expires_in_ms": 60000
  }
}
```

```sh
sashiko inspect read --session play-1 --world game --snapshot snap-91 --object p-2 --fields held_key
```

この場合、拒否時に必要だった鍵は `basement`、提示した鍵は `garden` とイベントから分かる。後続の `read` は同じ tick **終了時**の所持品を調べる。両者の間に鍵の持ち替えや個体の破棄が起こり得るため、判断に使った値はゲームがイベント発生時にコピーする。終了時に当事者が消滅していた場合もイベントは返し、採取できなかった項目には消滅理由を付ける。

### 入出力の約束

- 短い操作は引数で、複数個体・項目の一括取得や複合条件は `--request -` で標準入力から JSON を渡す。`snapshot` は指定した投影を一度で固定し、`read` はその範囲を何回でも参照できる。条件式は型を検査した比較・論理演算に限定する。
- 単発操作は標準出力に JSON 一件を返す。継続購読の `watch` は開始・データ・欠落・終了を区別した NDJSON を返す。案内や診断ログは標準エラーに出す。成功時は終了コード 0、失敗時は非ゼロと `{"ok":false,"error":{"code":"OBJECT_GONE"}}` のような機械判定可能な応答を返す。
- 接続時にプロトコルの版と利用可能な操作を取得する。ID・64 bit カウンターは JSON では文字列とする。値の欠損・未収録・無効な参照は理由を返し、正当な空値と区別する。`wait` の期限到達は `TIMEOUT`、「イベントが起きなかった」と判定できない履歴欠落は `HISTORY_GAP` とする。
- 観測は複数クライアントで共有できる。GUI は名前・タグ検索、画面ピック、ピン留め、個体間比較、参照移動を同じプロトコルに対応付ける。クエストや音源などクリックできない対象にも一覧から到達できる。

## ランタイムと履歴

1. ローカルの接続口で要求を解析し、型・要求量・操作権限を確認して有界キューに入れる。デスクトップの初版は同一ユーザーのローカル IPC を使う。実機の開発ビルドでは明示的に接続を許可し、接続相手を認証する。CLI、エディタ、テストで共通の要求処理を使う。
2. ゲーム側は各ワールドの更新ジョブが完了した境界でコマンドと採取を処理する。ワールドを借用するのはこの短い期間に限り、クライアントへの送信と JSON 化はコピーの公開後に行う。未接続なら採取を休止する。接続後も索引・採取・転送・履歴にそれぞれ予算を持たせ、展開中のページと購読項目を優先する。
3. 値の購読は最新の確定版へ追いついてよい。イベントはワールド内の順序付きカーソルで有界リングに保持し、生成・消滅も記録する。並列処理のイベントには生成元とローカル順を保持し、確定時に統合した順序を示す。因果関係を主張するイベントは原因イベント ID を明記する。
4. フィールド条件は tick 境界で、瞬間的な判断はゲームが発行したイベントで評価する。条件付き停止は該当 tick を完了してから停止し、当たったイベントと停止時点を返す。`pause` 中も要求処理・描画を継続し、`step` は一更新、`resume` は連続更新へ戻す。制御権は一度に一クライアントに与え、切断時にホストが回収できるようにする。
5. 履歴は記録開始以降のデータを対象とする。消滅した個体は記録済みの最終値と消滅時点を参照できる。切断後はセッション ID と最終カーソルで再購読し、保持範囲を超えたら欠落区間を返す。過去画面から進めるのは記録の閲覧であり、ゲームを過去から再実行する場合は別セッションとして起動する。

負荷が上限に達したら、要求の縮小または再試行が可能な容量エラーを返す。クライアントの遅延でゲーム更新を待たせない。診断用のバッファを準備時に確保し、通常更新で増設しない。出荷構成では収集コード、診断専用の型記述・文字列・保持領域、接続口、通信依存をビルドから外す。最適化した開発構成でも観測できるようにする。[フレームメモリ方針](implementation-policy.md#steady-state-memory)・[検証方針](../guides/validation-policy.md)

## 開発時の採取ジョブと報告の交換形式

ホストは接続時の `hello` で、対象 view、採取段階、静止画・動画などの利用可能な操作を返す。
未対応の操作を要求すると `UNSUPPORTED`、有界の受付枠が埋まっていれば `CAPACITY` を返す。
受理した要求には session 内で一意の job ID を返す。クライアントはその ID で進捗と終端の結果を
取得する。保存・符号化中も接続は他の要求を扱い、画像や動画は報告ディレクトリのファイルで渡す。

交換形式 v1 は `sashiko_inspect::report::Manifest` に定義する。専用ディレクトリに
最初に `manifest.json` を `outcome.state=recording` で公開する。書き手が強制終了した場合は
この状態が残る。正常終了は `complete`、利用できる部分と欠落を伴う終了は `partial`、
失敗は `failed` と理由を記す。書き手は成果物を閉じてから一時ファイルを rename して索引を
更新する。読者は一時ファイルを開かない。各ファイルは用途と報告内の相対パスで指定する。
版、session、world、job、build、asset 識別子、実行設定、要求時の tick を報告に保持する。
64 bit の frame・tick・単調時計の経過 ns は十進文字列で交換する。

たとえば tick 40 で保存を要求し、描画せずに tick 41 と 42 が進み、次の描画 90 と 91 が
ともに tick 42 を使った場合、`requested_tick="40"`、両画像の `tick="42"`、異なる
`frame` を記録する。tick 41 の入力やイベントは tick 履歴から参照する。描画のない tick は
画像の取りこぼしに数えない。描画 92 が読出し枠の枯渇で採れなければ
`{"unit":"frame","first":"92","last":"92","reason":"capacity"}` を gaps に残す。
各画像は view、出力寸法、段階（例 `final_srgb_ui`）、セッション開始からの経過 ns、
元 tick と直前 tick の補間係数（補間しないときは null）を持つ。再提示だけの試行は
同じ描画を参照する。これにより表示順、固定更新、非同期ファイル保存の完了順を識別できる。

Survivor の `diagnostics` 構成では、描画なしの報告も作成・照合できる。

```sh
cargo run -p survivor --features diagnostics -- --headless --ticks 120 --record-report report-120
cargo run -p survivor --features diagnostics -- --headless --verify-report report-120
```

報告は新しいディレクトリに作る。`replay.json` に tick 0 のアリーナ、シナリオ、乱数 seed、
ルール版と以降の入力を含める。`ticks.ndjson` は確定状態、ゲームイベント、群衆・弾・
ドロップ・乱数列・アニメーションなどの指紋を更新順に持つ。検証は記録時の physics worker 数で
先頭から再生し、最初の状態差の tick と比較値を返す。公開状態とゲーム側の指紋を照合する
範囲に、物理エンジン内部のキャッシュは含めない。開始データの不足・改変を識別し、
成功時も記録時と再生時の実行ファイルの SHA-256 を返す。

Windows では `cargo run -p survivor --features diagnostics -- --debug-dir reports` で
プレイし、**F8** で次の描画を保存する。PNG はゲームの HUD を含む。OS のウィンドウ枠は含まない。
実行時の出力フォルダは標準エラーに表示する。`--inspect-stdio` も指定すると、同じゲームに
下記の NDJSON を送れる。応答の job 値を `job` 操作に渡すと、待機、GPU 読出し、書込中、
完了、失敗を識別できる。取得中も `find`、`read`、`watch`、`pause`、`step` が使える。

```json
{"id":"1","op":"hello"}
{"id":"2","op":"capture","request":{"action":"report"}}
{"id":"3","op":"job","job":"<session>/j1"}
```

報告はセッションと受付 ID ごとの新規ディレクトリに保存する。入力・状態は tick 0 から
最大 216,000 更新（固定長の計測実行では指定フレーム数）を保持する。枯渇後に終了状態を再生
できなければ欠落を記録する。画面なしで PNG も生成する場合は `--headless --ticks 120
--backend vulkan --width 640 --height 360 --record-report report-120` を指定する。

**F9** で無音録画を開始・停止する。NDJSON では `capture` の request に
`{"action":"start_video","extent":[640,360],"fps":30}` または `{"action":"stop_video"}` を
渡す。停止ジョブの結果に報告ディレクトリが入る。Matroska の FFV1 動画と
`frames.ndjson` でデコード順、PTS、採取元 frame、tick、時刻、リサイズ前後の寸法を追える。
表示を出力寸法へ最近傍で縮尺変換する。PTS の単位は指定 fps の逆数で、欠落の理由と
区間を manifest に記録する。符号化が遅い場合も準備した RGB バッファ三枠の範囲で続行する。

符号化は開発者の Python、PyAV、NumPy を子プロセスとして利用する。
`SASHIKO_VIDEO_PYTHON` で Python の場所を指定できる。診断起動時の FFV1 能力照会に
失敗すると、hello は静止画の操作を提供し、動画の要求は `UNSUPPORTED` を返す。
ゲームの出荷物に Python・PyAV・FFmpeg バイナリを同梱しない。
[PyAV の符号化 API](https://pyav.org/docs/stable/cookbook/numpy.html)・[FFmpeg の配布条件](https://ffmpeg.org/legal.html)

`python tools/diagnostics/timeline.py show REPORT --frame N` で、その描画の元 tick、
入力、ゲームイベント、tick 終了時のスナップショットを読む。`--tick N` なら描画しなかった
更新も指定できる。引数を省くと全更新を時系列で出力する。被ダメージでは判断時の HP・
突進フラグ・敵 ID と終了時の位置を表示する。記録対象外は `NOT_CAPTURED`、終了時に
加害個体が消えていれば `OBJECT_GONE` になる。保存された投影は期限切れにならない。
期限つきライブスナップショットの read は満了後に `SNAPSHOT_EXPIRED` を返す。

同じ標準入出力接続を保つには `python tools/diagnostics/timeline.py live -- survivor
--debug-dir reports --inspect-stdio` で起動する。F8 の保存先を `open DIR` で開き、
`frame N` → `read actor` でその実行中の個体を調べる。`find`、`wait`、`watch`、
`pause`、`step`、`resume` と生の NDJSON 要求にも対応する。異なる session や world で
過去のハンドルを再利用しない。

画面ピックは表示成功時の view、フレーム番号、元 tick と、ゲームが提供する個体の選択範囲を
一緒に公開する。Survivor は身体の投影楕円を使い、重なりはカメラに近い個体を選ぶ。
選択範囲はモデルの輪郭や背景とのピクセル単位の遮蔽を表すものではない。
`pick` の `pointer` に view、point、viewport（表示領域の左・上・幅・高さ）を指定する。
`frame` を指定した過去フレームの期限切れは `FRAME_EXPIRED`、空背景は `empty`。
resize 時は次の表示成功まで選択範囲を失効させる。選択済み個体が消滅した後の
`selected` は元の ID と `OBJECT_GONE` を返す。

### 前後クリップ

`--debug-dir reports --clip-history` で 160×90・10 fps の RGB 履歴を準備する。
F10 または `{"action":"clip","trigger":"test_failure"}` の要求で、最初のトリガーを
含む 100 ms 枠を中心に前 50 枠、後 20 枠を採る。プレイヤーへのダメージ、報告の
書き込み失敗もトリガーになる。`--clip-frame-ms 50` を追加すると表示間隔が 50 ms
を超えたときに採取する。同じ区間への要求は最初のジョブを指す `linked` を返し、
終了時刻を延長せず、原因別の件数と最初・最後の tick と時刻を記録する。

画素履歴は 71 枠（3,067,200 バイト）。書き出し時に対象枠を一度複製し、一つの
ワーカーが FFV1 とフレーム対応表を保存する。その間も履歴を更新する。新たな
書き出しを受け付けられない場合はジョブが失敗理由を返す。起動前、描画なし、
読み戻し待ち、途中終了の不足は manifest の `clip_sample` の区間に残る。映像が
一枚もなくてもトリガー・入力・イベントの報告を保存する。

### 表示レイヤーと深度

Survivor の `--debug-dir` 実行で `hello.diagnostics` にビュー、採取段階、切替可能な
レイヤーが出る。たとえば次の要求を送り、ジョブが `applied` になった後に F8 で
保存すると、HUD を消した状態で、プレイヤーと最寄りの敵の衝突半径が緑で映る。

```json
{"id":"1","op":"capture","request":{"action":"set_layers","layers":{"hud":false,"collision":true,"velocity":true,"ai":true}}}
```

水色はプレイヤーの直近の固定更新での速度を 0.25 秒分に換算した線、紫は最寄りの
敵からプレイヤーへの目標線。ゲームは `sashiko::ui::debug::DebugDraw` にカテゴリ付きの
線・楕円・ラベルを渡す。HUD と合わせて準備済みの 256 描画を使用し、長い線は点線で
表す。表示設定は次の変更まで続き、PNG と動画の各フレームに設定が残る。

`{"action":"report","view":"main","stage":"scene_depth_d32"}` では、シーン描画後、
合成前の正規化デバイス深度を採る。`depth.f32le` は上から順に並ぶ D32 の
リトルエンディアン生値で、行末パディングはない。`frame.png` は 0〜1 を 8 ビット
グレーにした確認用画像。Survivor は単一サンプルの main ビューを公開する。
4× MSAA のシーン深度は描画時に破棄されるため、Renderer は取得要求を拒否する。
深度の録画は提供していない。

## 実行中の編集と制作元への保存

実行値は既定で読み取り専用とし、ゲームが編集可能と宣言した項目にだけ変更要求を送れる。たとえば「最大 HP を変更する」には、現在 HP の再計算も含めた操作をゲーム側で定義する。表示用の反射情報は変更権限を与えない。

- **個体に試す。** 対象 ID、期待する対象の版、要求 ID、関連する変更の組を送る。所有者が生存・競合・不変条件を一括確認し、全項目を適用するか、変更前の状態を保って理由を返す。成功は実値と適用した tick・版を返す。一時停止中も編集だけを確定できる。
- **再送・競合を扱う。** 同一セッションで有効な再送期間を宣言し、同じ要求 ID と内容には前回の結果を返す。内容の異なる ID 再利用、古い版、再送期間外の再試行を拒否する。別の開発者が同時に調整した場合は、現在値を再取得して差分を判断できる。
- **制作元に残す。** 実行中の一時編集とは別に、制作ツールが配置または原型を選び、制作データの版、保存する差分、影響する配置を示す。明示的な確定でトランザクションとして保存し、制作側で Undo できる。制作元に対応する項目のない動的個体や現在 HP には保存操作を出さない。

## 実装順と受け入れ条件

| 段階 | 最初に通す操作 | 合格条件 |
|---|---|---|
| 読み取り | `sessions → schema/find → read/snapshot` をローカル CLI とヘッドレスで通す。 | ゲームを進めながら二つの CLI から一枚のスナップショットを読み、値が一致する。ECS と配列による小さなゲーム実装で同じ契約試験を通す。削除後のハンドル、期限切れ、収録範囲外を区別する。 |
| 原因調査 | `wait/watch`、履歴、条件付き停止、1 tick 送り、GUI ピックからの引き継ぎを加える。 | 扉の例で LLM が追加ログや再起動なしに拒否理由と当事者を提示できる。同一 tick で状態が元に戻る場合、個体が消える場合、取得が遅れた場合も、記録と欠落を正しく返す。 |
