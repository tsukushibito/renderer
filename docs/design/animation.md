# キャラクターアニメーションの設計方針

固定 tick でゲームに必要な動きを確定し、描画時には複数のビューとパスが同じ変形結果を共有する。CPU の評価単位はキャラクターのポーズ、GPU の変形単位はポーズを適用したメッシュの LOD とする。これにより、防具を追加しても歩行の評価は一度で済み、同じ防具を深度・影・本描画に使うときも頂点変形を共有できる。

CPU ポーズ評価は単精度で、整数 tick・ルート並進の倍精度積算から独立している。読込時のバインド逆行列・ローカル姿勢復元と試験用の参照計算は倍精度を使い、表示用データの変換時に有限性・スケール・回転を確認する。Survivor はクリップあたり 0・13・26・39 tick の位相を一括評価し、各ポーズを CPU で頂点に適用する。GPU スキニングとワーカー配分は今後の工程である。

`PoseBatch` は骨格、全身または部分ボーン集合、出力件数の上限を準備時に固定する。呼び出し元が確定した表示サンプルを入力順に受け、4 件ごとに同じボーンの 4 ポーズを SIMD レーンへ配置する。平行移動・スケール・回転の合成と親子行列積をまとめ、親を先に評価する。球面補間の重みは各レーンの角度から求める。残り 1〜3 件は逐次評価する。メモリの再確保やイベントの消費は行わない。ワーカーへの割り当て単位は独立したバッチとする。[精度と採用時の計測](../verification/current.md#animation-cpu)

逐次版の `Playback::advance_to` は前回を除く今回までのイベントとルートの並進差分を返す。時刻は単調増加で、時刻ゼロのマーカーは次のループ境界から発行する。クロスフェード中は固定 tick ごとの並進差分を区間中央の重みで混合し、イベントは遷移先から発行する。終端までは新しい遷移を開始できない。`evaluate_pose` は時刻を進めず、全骨格または祖先を含む準備済みの部分集合を評価する。表示用のランダムアクセスには `Clip::evaluate_at` を使う。

## 責務とデータの所有

| 所有者 | 入力、出力、寿命 |
|---|---|
| アセットクック | 骨格、クリップ、ボーンマスク、同期マーカー、イベントとルート移動曲線を取り込む。名前を ID に解決し、階層・参照・ウェイトを検査する。グラフを評価順と一時領域の配置に変換し、圧縮誤差は足先・手先などの位置でも評価する。 |
| `sashiko-animation`（新設） | 不変の骨格・クリップ・評価グラフを共有し、時刻、遷移、重み、サンプリング用キャッシュを個体が持つ。モデル空間のボーン姿勢、ルート移動差分、通過イベントを返す。ヘッドレスでも評価できるよう、ECS・Renderer・GPU API から独立させる。 |
| ゲーム／ECS | エンティティとアニメーション個体の対応を持ち、速度、照準、接地、必要なボーンと評価時刻を一括入力する。移動差分の物理への適用、攻撃判定、イベントの消費を担当する。 |
| Renderer | メッシュのジョイント対応表と逆バインド行列を使い、骨格の姿勢からメッシュ用パレットを作る。ビュー別の可視性・LOD、GPU 上の頂点、前回描画の履歴、完了後の資源回収を管理する。 |

基本機能はクリップ再生、状態遷移、1D/2D ブレンド、加算レイヤー、部分マスク、同期マーカー、ルートモーション、イベント、ソケットの姿勢取得とする。たとえば歩きながら狙う動作は、歩行と走行を速度で混ぜ、上半身に照準を加え、最後に手の IK を解く。胴体と防具はこの骨格姿勢を共有し、剣の取り付けには手のボーン姿勢を使う。

## CPU 評価と固定 tick

1. **入力を確定する。** ゲームは固定 tick ごとに入力を渡す。評価は進んだ時間区間から状態遷移、ルート移動差分、イベントを求める。ループ境界をまたぐ場合も区間ごとに拾い、描画の再試行で再消費しない。ワーカーは個体別の領域に書き、ゲームが tick、安定した個体 ID、クリップ内順序で結果を消費する。
2. **必要なボーンを決める。** 当たり判定用の手は画面外でも固定 tick で評価する。部分評価には対象ボーンの祖先と、IK などの制約が読むボーンを含める。遠景の表示用ポーズには頻度低減と補間を許し、ゲームのイベントと移動は固定 tick を維持する。
3. **個体間でジョブを配る。** 同じ骨格・評価プログラムの個体をまとめ、ホストの共通ジョブ実行器へ渡す。各ジョブは入力を共有し、出力を排他的に借りる。クリップを展開し、独立するトラックを SoA（成分ごとの配列）でまとめて補間し、ローカル姿勢をブレンドする。階層合成は親から子へ進める。個体間のバッチ分割で複数コアを利用する。実装済みの SIMD は同じ骨格の複数ポーズを対象とする。
4. **利用地点で待ち合わせる。** 物理は要求したゲーム用姿勢、Renderer は表示用姿勢の完了を待つ。少数個体には呼び出し元での逐次評価を用意し、ジョブ分割の閾値は骨数・層数とスケジューリング費を含めて測定する。

## GPU スキニングとマルチパス

まず全ビューの深度、影、本描画、速度などの要求を集める。事前カリングには変形を覆う保守的な境界を使い、メインカメラ外の影キャスターを含める。変形結果はモデル空間に置き、ワールド変換を描画時に適用する。共有にはメッシュ版、LOD、スキンバインド、同一の評価結果、モーフ等の追加入力の一致が必要になる。時刻や IK が異なる個体は別に評価する。

| 利用条件 | 選ぶ経路と理由 |
|---|---|
| 同じ変形を複数パス・ビューで使う | コンピュートで一度変形し、必要な頂点属性の和集合を書き出す。小さな仕事はまとめて投入し、静的な UV・色は元のストリームを読む。 |
| 影が別 LOD を使う | 頂点対応が異なるため LOD ごとに計画する。影しか使わない LOD なら位置だけを出力できる。 |
| 小さいモデルを一度だけ描く、またはキャッシュ容量に余裕がない | 同じパレットを読む頂点シェーダー経路を用意する。dispatch、出力書き込み、再読込の費用を含めて端末別に選ぶ。 |
| 速度を描く | 現在と前回描画の変形とワールド変換を使う。初出・テレポート・対応頂点のない LOD 切替では履歴を無効にする。 |

RenderGraph にパレット転送、コンピュート書き込み、頂点読み取りの範囲と依存を宣言する。最初の比較基準は graphics と同じキューとし、別の compute キューは対象機での対応と同期・所有権移転を確認し、独立した描画との重なりでフレーム全体が短縮した場合に採用する。GPU 完了、記録中の参照、速度用の履歴を含む最後の利用まで出力領域を保持する。[Vulkan の同期とキュー](../guides/vulkan-best-practices.md#synchronization)・[バックエンドの契約](vulkan.md)

個体、ジョブ、イベント、パレット、変形頂点、履歴の容量を準備時に予約する。予算内の通常フレームでは CPU ヒープの確保・再確保・解放と Renderer 起因のネイティブ資源作成・破棄をゼロにする。容量不足時は準備済みで同等の描画が可能な経路へ切り替えるか、必要量を返して明示的に再準備する。ゲーム用イベントの欠落、暗黙のバッファ拡張や GPU 待機は許容しない。保証済み資産の再走査はクック・ロード境界に集約し、同期、容量、寿命の保証は製品構成でも維持する。[定常フレームのメモリ方針](implementation-policy.md#steady-state-memory)・[検証方針](../guides/validation-policy.md)

## 既存システムから採用する判断

| 一次資料 | 利点と制約 | 設計への反映 |
|---|---|---|
| [Unreal Engine の Skeletal Mesh Rendering Paths](https://dev.epicgames.com/documentation/en-us/unreal-engine/skeletal-mesh-rendering-paths-in-unreal-engine) | Compute Skin Cache は変形済み頂点を再利用し、メッシュ LOD ごとに選択できる。高精細 LOD への切替でキャッシュ上限に届く場合がある。 | 全パスの要求と出力容量を集めてから経路を選ぶ。 |
| [Unity の OnStateMachineEnter](https://docs.unity3d.com/jp/current/ScriptReference/StateMachineBehaviour.OnStateMachineEnter.html) | 遷移をゲーム側で拡張できるが、このコールバックを実装するとステートマシンの並列評価が無効になる。 | 評価前に入力を確定し、結果はイベントとして評価後に渡す。 |
| [Godot の AnimationTree](https://docs.godotengine.org/en/4.7/tutorials/animation/animation_tree.html) | 状態機械とブレンド空間を作者が組み合わせられる。共有ノード資産を直接変更すると他個体へ波及する。 | 編集グラフを不変の実行用資産に変換し、可変パラメータは個体が所有する。 |
| [ozz-animation の並列実行](https://guillaumeblanc.github.io/ozz-animation/samples/multithread/)・[データ配置](https://guillaumeblanc.github.io/ozz-animation/documentation/advanced/) | 共有資産と専用作業領域でサンプル・ブレンド・階層合成を並列化できる。ジョブの粒度と競合回避は組み込み側が決める。 | クレートが出力範囲を安全に分割し、ホストが他の仕事と合わせて配分する。 |

## 実装順と受け入れ条件

| 順序 | 確認すること |
|---|---|
| 1. 独立クレートと逐次参照評価 | 描画なしで固定入力を再生し、ループ、遷移、ルート移動、イベント順、部分評価と全評価の対象ボーンが一致することを確認する。 |
| 2. CPU 並列評価 | 同じ入力でワーカー数と完了順を変え、ゲーム結果と順序を照合し、姿勢は規定の数値誤差内で比較する。少数の主役と群衆で骨数・ブレンド層・IK を変え、tick の p50/p95、最遅ジョブ、利用側の待ち時間を測る。 |
| 3. GPU の二経路 | CPU の参照変形と頂点・コンピュートの両経路で位置・法線・接線を照合する。複数ビュー、影だけの個体、履歴失効、容量枯渇、複数フレーム同時進行を実機で確認する。 |
| 4. 実機で経路と LOD を選定 | 同じ可視集合・画質で単一パス、深度＋本描画、複数の影を比較する。統合 GPU と独立 GPU でフレーム時間、変形時間、出力バイト数、ピーク常駐量を記録し、CPU メモリ操作とネイティブ資源操作も別々に数える。 |

上記は今後の受け入れ条件である。実測時には対象機・構成・負荷と未確認範囲を[現在の検証状況](../verification/current.md)に記録する。
