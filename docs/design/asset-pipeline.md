# ゲームエンジン向けアセットパイプラインの到達設計

鎧の色を編集した制作者は、その鎧を着たキャラクターをプレビューで確認できる。ゲームは同じ鎧を装備 ID で保存し、ファイルを改名しても次回の起動で復元できる。街に同じ鎧の住人が百人いても、色の変更で百回の画像転送や街全体の再準備は起きない。この体験をエディター、製品、ビルドサーバーで成立させることを到達目標とする。

**オフライン側は対象プロファイルで利用可能な成果物とその組合せを確定する。オンライン側は、その中から現在の用途・実機・予算で使えるものを選び、安全に公開する。** ここでいうオンラインはプレイ中・プレビュー中の実行を指す。ローカルに配布済みのゲームはネットワークを必要としない。本章は描画アセットについての目標契約である。既存の部分実装と、初版で実証する範囲は末尾に示す。

## 既存エンジンから採る判断

下表は 2026-11-24 に確認した各社の公式資料による。制約は資料が扱う方式の範囲に限定した。右列は本プロジェクトでの設計判断であり、エンジン間の性能順位を表すものではない。

| 方式 | 得られる利点と払うコスト | この設計への反映 |
|---|---|---|
| Unity 6 の Asset Database | 原本の隣に GUID と取込設定を置き、依存と成果物をキャッシュできる。キャッシュを復元できても、原本とメタデータの対応を失うと参照の復元に影響する。[Asset Database](https://docs.unity3d.com/6000.0/Documentation/Manual/asset-database-contents.html) | ID と取込設定を原本とともに版管理する。派生キャッシュを消した状態からも同じ参照と成果物を復元する。 |
| Unity Addressables 2.7 | カタログ更新で未変更バンドルの再配布を省ける。一方、更新ビルドでは全コンテンツを再ビルドする方式があり、元リリースの状態ファイルも要る。別アセットの依存が同じバンドルのロードに波及し、残る利用者がバンドルの解放を遅らせる。[更新ビルド](https://docs.unity3d.com/Packages/com.unity.addressables@2.7/manual/content-update-builds-overview.html)・[バンドルの依存](https://docs.unity3d.com/Packages/com.unity.addressables@2.7/manual/memory-assetbundles.html) | cook の再実行量、配布量、常駐量を個別に測る。物理的に同梱した別アイテムまで実行時の必須依存にしない。 |
| Unreal Engine の Derived Data Cache と Asset Manager | 共有キャッシュがチームの重複変換を減らす一方、遠隔接続では取得時間が再生成の利点を上回り得る。Primary Asset と名前付き Bundle は用途別にロード対象を選べるが、分類と保持するハンドルの管理が必要になる。[DDC](https://dev.epicgames.com/documentation/unreal-engine/using-derived-data-cache-in-unreal-engine)・[Asset Manager](https://dev.epicgames.com/documentation/unreal-engine/asset-management-in-unreal-engine) | 共有キャッシュ停止時も原本から cook できる。装備一覧・装着・高精細表示を用途として宣言し、どの要求が常駐を必要としているかを追跡する。 |
| Unreal Engine の PAK パッチとテクスチャストリーミング | プラットフォーム共通の PAK パッチ手順では配布済み cook と比較できるが、変更した package が単位になり、新旧 PAK が保存領域を使う。実行時には視点から欲しい mip を決め、プール予算に応じて品質と転送量を調整する。[PAK パッチ](https://dev.epicgames.com/documentation/unreal-engine/how-to-create-a-patch-in-unreal-engine)・[Texture Streaming](https://dev.epicgames.com/documentation/en-us/unreal-engine/texture-streaming-overview-for-unreal-engine) | パッチの境界と画面上で使える最小品質を独立させる。最低品質の表示時間と目標品質への到達時間を別に測る。 |
| Godot の import とバックグラウンドロード | UID は移動・改名をまたげる。原本と取込設定から生成物を再作成できる。原本を直接開く経路は export で失敗し得る。また、バックグラウンド要求でも未完了で結果を取得すると呼出元が待つ。[Import process](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/import_process.html)・[ResourceUID](https://docs.godotengine.org/en/stable/classes/class_resourceuid.html)・[Background loading](https://docs.godotengine.org/en/stable/tutorials/io/background_loading.html) | プレビューと製品は同じ成果物ローダーを使う。通常フレームは要求の準備状況を待たずに取得する。 |
| Godot 4.7 の PCK | パックの追加配布や差分圧縮が可能。同一パスへの上書きはマウント順に依存し、差分の連鎖はロード時間を増やす。[PCK と差分配布](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_pcks.html) | 一回の要求が使う世代を固定する。差分配布は復元時間、必要な空き容量、巻き戻しまで含めて選ぶ。 |

## 原本からゲームまでの受け渡し

| 境界・所有者 | 入力から出力へ | 成功の意味 |
|---|---|---|
| 制作・エンジン | 原本、永続 ID、編集した取込設定 → 版管理されたプロジェクト | 原本の移動後も参照を解決でき、意図しない複製 ID や壊れたサブアセット参照を制作時に診断できる |
| オフラインの import・cook | プロジェクトと対象プロファイル → 型・形式版のある不変な成果物 | 必須参照、材質の意味、頂点・インデックス等の整合を確認し、どの入力を読んだか説明できる |
| 配布ビルド・インストール | 配布の起点と用途 → 成果物集合と世代付きカタログ | 必須依存が解決でき、対応する製品版がその世代を開ける。ローカルでの切替前に必要ファイルを揃える |
| オンラインのエンジン | ID、用途、優先度、カタログ世代 → 準備要求 | 実機で使える候補と最小の必須集合を選ぶ。同じ成果物を使う並行要求は読み込みを共有できる |
| Renderer とエンジン | 検査済み描画入力 → GPU 準備 → 装備等の表示切替 | Renderer は安全に描画可能な版を返す。エンジンが要求先の生存と要求の鮮度を確認して採用する |

例えば、制作側は同じ画像の sRGB 用途と法線用途を区別して mip と圧縮形式を生成する。ロード側は対応形式を実機で確認して候補を選択する。必要なテクスチャ形式を扱えない場合は、宣言済みの代替か、対象 ID と理由を伴う失敗を返す。シェーダーも対象別バイナリと binding ABI を用意する。配布ハッシュはバイトの同一性を検証するために使い、プログラムのアクセス範囲などは既存の[外部シェーダー契約](implementation-policy.md#external-shader-assets)に従う。

### ID、版、依存の粒度

- **永続参照。** セーブやシーンは型付きの `AssetId` を記録する。ゲームに公開するサブアセットも再インポートをまたぐ ID を持つ。改名は ID を維持し、意図した複製には新 ID を割り当てる。DCC ツールで要素の順序や名前が変わり対応が曖昧になった場合は、元の参照と候補を制作者に示す。削除済み ID は再利用せず、置換やセーブ移行はゲームが明示する。
- **ビルドの同一性。** cook のキーは入力バイト、実際に読んだ依存、正規化した設定、変換器・外部ツールの版、対象プロファイルから作る。出力バイトは別途ハッシュ化する。同じ出力は別の論理アセットからも共有できる。パス探索順、時刻、並列完了順を成果物に混ぜず、固定したツールチェーンでクリーンビルドと差分ビルドを照合する。ライトマップなどのベイクは静的配置・材質・光源のうち実際に使う入力を宣言する。
- **参照の意味。** ビルド時に内容を読む辺は変更時に変換を再評価する。実行時に ID で解決する辺には、用途ごとに必須・任意を付ける。例えば色画像だけの変更ならメッシュ変換を省けるが、その画像から拡散反射を計算するベイクは再評価する。変換依存の循環と、公開前に互いの準備完了を要求する循環は依存経路付きで診断する。単に相互参照できるデータまで再帰的にロードしない。
- **世代とハンドル。** 一つのカタログ世代は、各 ID の候補を型・形式版・対象能力・用途依存・サイズ・ハッシュと格納位置に結び付ける。一回の要求とその依存解決は同じ世代を保持する。実行中の Renderer ハンドルは各デバイスでの一時的な所有を表し、セーブやカタログには書かない。

### ビルド、パッケージ、更新

照明を生成するホストは、表面を `prepare_surface_bake`、プローブを `prepare_probe_bake` で別々に準備する。準備結果の `execution()` から実際の方式、アダプター、ドライバー、使用シェーダーを取得できる。準備した処理が同じデバイスで計算を完了する。例えば表面に Vulkan Ray Query を使う条件でも、プローブには Compute を使う。自動選択で CPU に切り替われば、CPU 用の実行条件を記録する。GPU の準備や破棄はオフラインの境界で行い、既存の完了待ちと検証モニターの契約を引き継ぐ。

Bistro のビルド記録では、シーンと照明の入力識別子、時刻条件、ステージごとの設定、実行環境、実行ファイルとシェーダーのハッシュから表面・プローブそれぞれのビルドキーを求める。端末が配布データを検証する際には実際に書き出した索引・成果物のハッシュを使う。固定環境の反復試験は共有を許す条件を調べるために行う。同じ入力をすべてのビルドで二度計算する必要はない。GPU と CPU の比較には既存の許容誤差を適用し、出力バイトが一致する環境の確認は別途行う。[実行方式](../../crates/renderer-bake/src/execution.rs)・[Bistro のビルド記録](../../crates/renderer-bistro/src/bake/provenance.rs)

変換器は入力の形式ごとに原本を読み、後段の cook は描画に使う型付きデータを処理する。通常のモデルはローカル座標のメッシュを共有し、変換行列をインスタンスに持たせる。Bistro のように配置を焼く静的シーンでは、その選択をレシピに記録する。用途を追加したときは対象型の変換・ロードを追加でき、既存ゲームの ECS や RenderGraph に原本の知識を持ち込まずに済む。

ビルドは変更された入力から逆依存を辿る。開発者のローカルキャッシュと任意の共有キャッシュは再生成できる。配布したカタログ、そこから参照できる成果物、対応する実行ファイル・形式版の記録は、再配布・巻き戻しを支えるためリリース単位で保存する。ツールは「なぜ再生成したか」「どのマップや装備から参照されるか」を説明できるようにする。

配布では、起動・レベル・DLC 等の起点から用途別の依存を求める。個別ファイル、パック内の範囲、追加ダウンロードを同じ論理参照で表せるようにする。用途上独立したデータは、コンテナ内でも必要部分を読み出せる圧縮・索引単位を選ぶ。パックを細かくする利点は部分取得と更新にあり、コストは索引、ファイル数、I/O 要求、重複である。共有アセット一つの更新について、再 cook したバイト、配布バイト、端末での復元時間、復元用の一時領域の最大使用量を別々に比較して配置を決める。

成果物を先に確定し、互換な reader、必須参照、サイズ、完全性を確認したカタログを最後に公開する。端末側でも候補世代の導入が途中なら直前の利用可能世代から起動する。任意パックが未導入なら、その用途は取得待ちか明示した代替に遷移する。未知の必須形式は部分的に適用する前に拒否する。更新・ロールバック中も、使用中または復旧用に保持する世代から到達できる成果物は削除しない。実行形式との互換範囲と保持世代数は各リリースで決める。

### 実行中のロードとホットリロード

装備一覧にはアイコンを、装着には最低品質のメッシュと材質を要求する。ロード要求には装着先・スロット・要求番号を持たせ、I/O・展開は成果物の版、GPU 準備はさらにデバイスと使用条件で共有する。一人が装備を外したらその人の要求を解除する。他の利用者が残る転送は続け、不要になった投入済み転送は完了後に回収する。制作者のホットリロードも、同じローダーで新しい世代を要求する。

新しい鎧を装着する際は次の順序を守る。

1. 用途の必須集合に対し、CPU 展開、staging、GPU 常駐、同時ジョブの予算を確認する。旧版、準備中の新版、退役待ちも計上する。予算不足なら低品質の候補、延期、明示的な再準備からホストが選ぶ。
2. ワーカーが必要範囲を読み、外部バイトの形式版、サイズ・範囲・演算の上限、完全性を取込境界で検査する。描画側は準備済み容量内で変更分を分割投入し、未完了を待たずに返す。要求数・バイト・優先度を制御し、古い先読みが画面に必要な資源を塞がないようにする。
3. 必須集合が安全に参照できた時点で、まだ最新の要求ならフレーム境界で一括採用する。高精細 LOD・mip は後から独立して昇格できる。破損、取消、非対応、容量不足では途中まで準備した版を表示しない。初回ロードで旧版がない場合の代替表示や起動失敗は用途ごとに決める。
4. 古い版は記録中の参照、投入済み GPU 処理、関連する表示、CPU の保持結果が解放されてから回収する。任意の処理に失敗しても、受理済み転送と保持者を追跡して再試行できるようにする。[資源の準備と寿命](vulkan.md)・[メモリ方針](implementation-policy.md#steady-state-memory)

例えば新版の cook が成功し、GPU の空き容量だけが不足した場合、カタログは新版を公開できる。ゲーム内の装備は旧版の表示を継続する。この二つの状態を個別に照会できれば、制作者は再インポートと GPU 容量の調整のどちらが必要か判断できる。詳細な依存トレースや保持理由の収集は開発構成に置き、製品にも必要な容量・所有・同期・失敗処理は全構成に残す。[検証方針](../guides/validation-policy.md)

## 現行実装、初版、最終形の受け入れ

### 描画・ベイク API に求める契約

**準備と採用。** エンジンは同じ成果物を使う複数の装備に画像所有者を共有させる。描画に渡す画像ビューは初期化済みの mip 範囲を表し、現在のデバイスで形式・用途を使用できることを準備時に確かめる。準備中の候補を保持したまま旧装備で次のフレームを描ける。進行一回に使う転送バイトと投入件数に上限を設け、準備完了と、現在の装着先への採用は独立させる。採用前に対象ビューの登録と旧版の退役先を確保する。失敗なら旧装備を描き続け、成功後は最後の利用が終わるまで旧資源を追跡する。

**材質のサンプリング。** 画像とサンプラーの組を base color・normal・ORM・emissive ごとに記録する。glTF の U/V のアドレス指定、拡大フィルター、縮小フィルターと mip 選択を独立して解釈する。未指定時は repeat と線形フィルター、mip 間線形を採用する。アルファマスクは本描画と影で同じ base color の設定を使う。ベイクの表面サンプルには画面上の微分がないため、ベイク入力の mip 0 をマップごとの拡大フィルターで評価する。制作時に縮小した画像をベイク入力にする場合、その選択もレシピに含める。[glTF 2.0 のサンプラー](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#samplers)

**ベイクの再利用。** 同じ入力・レシピから生成し直せる範囲を特定するため、表面とプローブで実際に選んだ実行方式を区別し、結果に影響する設定・ツール・デバイス情報を記録する。キャッシュ候補を探すビルドキーと、完成バイトを識別する成果物ハッシュを別々に持つ。同条件の反復ベイクは再利用範囲を検証する試験で行う。配布済みデータの読込みに再ベイクは要らない。

**ページ単位の配布。** 配置索引と GPU 転送用ページ、プローブに独立した版を持たせる。一つの表面を描くのに必要な前面・背面と配置情報をオフラインで確定する。固定した配置で調べるページを選べる一方、間接光の計算にはページ外の遮蔽物や発光面も影響する。再計算範囲を狭めるときは、照明の依存範囲をビルド側で保証する。

### 実装状況と受け入れ手順

[Bistro の cook](../../tools/bistro/cook.py) は配置を焼いた頂点・インデックスと、用途別の画像・サンプラーを生成する。静的照明は表面とプローブの実行条件を別々に記録し、世代索引から必要な照明ページを選んで読み込める。[訓練場の装備要求](../../crates/training-yard/src/yard/equipment.rs) は要求世代と装着先を追跡する。

標準 Renderer では、起動時の `prepare_assets` とプレイ中の [AssetCandidate](../../crates/renderer/src/pipeline/setup/candidate.rs) が同じ転送・公開処理を使う。プレイ中は変更対象だけを候補に含め、`poll_candidate` に各回の転送バイト数・投入回数の上限を渡す。完了後に `commit_candidate` で全ビューへ反映し、最後の利用者が手放した資源を同時に退役させる。要求が古くなった場合は `cancel_candidate` を呼ぶ。ホストが Runtime を直接扱う間は自分のフレーム ID を指定して `wait_for_frame(id, Duration::ZERO)` を使い、アセット転送の完了は `poll_candidate` または `collect_assets` に回収させる。画像の常駐 mip 範囲を広げる手順は [SceneRenderer](../../crates/renderer/src/pipeline/setup/scene_renderer.rs)、検証範囲は[検証記録](../verification/current.md#asset-preparation)に示す。

**初版で通す一本の経路。** glTF の静的装備一つをモデルローカル座標で cook し、標準 PBR 材質・画像を個別ファイルとカタログで訓練場に配布する。初版から ID と版、用途依存、変更分の要求、未完了・失敗、表示への採用を区別する。ロード画面では既存の同期準備を使える。プレイ中の無停止切替の合格には、増分投入と完了照会による実機確認が必要になる。

**大規模化の判断。** 同時要求が増えたら優先度・帯域・退役予算を使う増分ストリーミングを実証する。多数の制作端末で同一変換が繰り返されるなら共有キャッシュ、配布や起動の I/O が支配的なら分割索引とパックを評価する。いずれも同じ成果物契約で置換できる。数値予算は対象機・ストレージ・代表シーンを固定して測定後に設定する。

| 段階・実験 | 比較する条件と合格の判断 |
|---|---|
| 初版・原本からの復元 | 改名・移動後もセーブの装備 ID を復元する。空キャッシュのビルドと差分ビルドでハッシュを照合する。原本・Python・変換キャッシュを外しても配布物だけで装備が表示される。 |
| 初版・共有画像の編集と失敗 | 再実行した変換と理由を記録し、画像を読まないメッシュ変換が走らないことを確認する。壊れた入力では直前のカタログ、破損した配布物や準備失敗では直前の表示を維持する。 |
| 実行時・競合と寿命 | 二つの要求の完了を逆順にする。共有する利用者の片方を削除し、旧フレーム結果を保持したまま連続更新する。要求先の誤更新、重複転送、早期解放がなく、保持解除後に予算を回収できることを両 API で確認する。 |
| 規模・総登録数と利用数を独立に変える | 使用集合を固定してカタログ規模を例として 10 倍にし、一件の変更が全件走査や全件転送を起こさないことを計数する。次に同じ装備の利用者だけを増やし、インスタンス更新数と、共有成果物の読込・GPU 転送回数を別に測る。 |
| 予算・プレイ中のロード | 低速 I/O、staging 枯渇、旧版保持を再現する。最低・目標品質までの時間、描画スレッドの停止時間とフレーム時間分布、CPU・staging・GPU のピークを記録する。準備済み上限内の通常フレームは CPU ヒープ確保・再確保・解放と Renderer 発行の native 作成・破棄を別々に 0 件と確認する。Vulkan・D3D12 の検証有効構成と診断なし最適化構成で既存の実機ゲートを通す。 |
| 配布・部分失敗からの復帰 | 更新を途中で中断し旧世代で起動、再開後に新世代へ移行する。任意パック欠落、非対応形式、旧世代への巻き戻しを検査し、転送量と復元用の空き容量を記録する。 |

これらは受け入れ条件である。対象パイプラインの実測値は実装後に[現在の検証状況](../verification/current.md)へ記録する。
